# ADB Runtime evidence record

Status: reviewed

ADB Runtime asks whether a live ADB transport on this device contradicts what init reports about
adbd. Danger means that report was contradicted in both samples: either a local endpoint answered
with the AOSP ADB first packet for the service type it advertised, in two discovery passes, or a
socket adbd leaves behind was still visible, while init.svc.adbd stayed stopped. It
does not claim which component is wrong, nor that resetprop, root or a particular hiding
implementation caused the inconsistency. A clean result only means that no contradiction was
observable from this app process.

## Sampling

Settings, init/property state, the init socket, the JDWP control socket and USB state are sampled twice; the second sample starts at least
1.5 seconds after the first sample starts. The interval is only a debounce against one-shot
transitions, not a claim that AOSP's USB recovery windows have expired: UsbDeviceManager's own
function-switch and enumeration timeouts are longer (Android 11 SET_FUNCTIONS_TIMEOUT_MS and
ENUMERATION_TIME_OUT_MS, lines 1676-1692, scheduled together at lines 1910-1916:
https://android.googlesource.com/platform/frameworks/base/+/1d9b9ab57d844b18b3b1b4297725141e7788109b/services/usb/java/com/android/server/usb/UsbDeviceManager.java#1676),
which is why no Settings or USB disagreement is ever promoted to danger.

Network discovery runs one 1.5-second window per pass that browses every ADB service type the
platform defines at once. The first pass runs with the first state sample. A second pass runs after
the second state sample only when the first pass protocol-confirmed an endpoint: a hard network
finding needs both passes to confirm the same endpoint, so without a first confirmation a second
pass could not change the verdict.

Property strings are interpreted by typed `AdbPropertySnapshot` accessors shared by domain rules and presentation. Daemon state distinguishes RUNNING, STOPPED, an unknown present value (OTHER), and an absent property (null); only STOPPED can satisfy the stopped-daemon contradiction precondition. This refactoring preserves running/stopped case handling, comma-separated USB function matching and the exact `persist.sys.test_harness=1` check; unknown and absent values remain informational and the severity rules are unchanged.

### Settings and lifecycle context

- Observable signal: Settings.Global adb_enabled, Settings.Global adb_wifi_enabled, UserManager.DISALLOW_DEBUGGING_FEATURES, persist.sys.test_harness, and init.svc.adbd.

### init service socket

- Observable signal: whether the `/dev/socket/adbd` inode that init creates for `service adbd` resolves from this process, compared against a sibling control name in the same directory that cannot exist.
- Producing subsystem: init's per-service socket table (system/core/init), the `adbd_socket` SELinux type, and the adbd process that inherits the descriptor.
- Mechanism: init.usb.rc declares the service as `socket adbd seqpacket 660 system system` with `disabled` on every release from Android 10 to 17, so the path can only appear once a trigger starts adbd. init creates and labels the inode while the service starts, then removes it while reaping, before it publishes `init.svc.adbd=stopped`. Android 11 and later unlink the path directly in `Service::Reap()`; Android 10 reaches the same point through its descriptor classes, where `Service::Reap()` cleans each descriptor and the socket's `Close()` unlinks the file. The order is the same either way. Applications may list and search `/dev/socket` because every domain holds `r_dir_perms` on `socket_device`, but no app rule grants anything on the `adbd_socket` label: the only allow belongs to system_server, and `neverallow appdomain adbd_socket:sock_file write` records the app ban on every release since Android 10. A present inode therefore answers `stat()` with EACCES while an absent one fails path lookup with ENOENT, and the sibling control name separates those two from a directory this process cannot resolve at all.

No run with adbd stopped was captured, because stopping the daemon ends the scan's own transport.

### JDWP control socket

- Observable signal: the errno of one `connect(AF_UNIX, SOCK_SEQPACKET)` to the abstract address `@jdwp-control`.
- Producing subsystem: adbd, which binds the listener, and the SELinux `unix_stream_socket connectto` check.
- Mechanism: this listener is the JDWP control channel, not a command channel for adbd. A process that wants to be debugged connects to it and hands adbd the socket the debugger will talk over, which is why app domains may reach it. adbd creates it itself: Android 10 binds `JDWP_CONTROL_NAME "\0jdwp-control"` as `SOCK_SEQPACKET` and calls `listen(4)` in its own `jdwp_service.cpp`, from Android 11 the same call lives in `libs/adbconnection` as `adbconnection_listen()`, and from Android 16 the literal sits in that library's `common.cpp`. The source spells the address `"\0jdwp-control"` because a leading zero byte is what marks an abstract name inside `sun_path`; Android 10's own file header says `@` is shorthand for that zero byte and `/proc/net/unix` renders it the same way, so `@jdwp-control` and the literal name one socket. No release binds an abstract socket called `adbd`: init creates `/dev/socket/adbd`, exports the descriptor as `ANDROID_SOCKET_adbd`, and adbd takes it back with `android_get_control_socket("adbd")`, which first verifies that the descriptor's own address is that path. The kernel resolves an abstract address by name and socket type before it consults the LSM, so a missing listener fails with ECONNREFUSED before any policy check while a matching one reaches SELinux. Policy reads the same on every release: `allow appdomain adbd:unix_stream_socket connectto` has shipped since Android 10, in `public/app.te` for 10, 11 and 12 and in `private/app.te` from 13 when the split moved, so a running adbd accepts the connect and EACCES appears only where an OEM removed that grant. Only a connect and a close are issued from a narrow JNI probe; no bytes are written, so no JDWP handshake starts.

### Network ADB mDNS

- Observable signal: API 29+ legacy _adb._tcp and API 30+ _adb-tls-connect._tcp resolved through NsdManager to an address owned by this device.
- Producing subsystem: adbd legacy TCP or Wireless Debugging listeners, mDNS/DNS-SD publishers, and Android NSD.
- Mechanism: Android 10 setup_port() advertises active legacy TCP ADB as _adb._tcp. Android 11 adds _adb-tls-connect._tcp for the secure-connect transport. On API 30+ Duck browses both types in the same window and prefers a local secure-connect endpoint over a legacy one, so both passes of a scan pick the same listener; API 29 browses only legacy. Discovery keeps browsing after one instance fails to resolve, and found instances are resolved one at a time because NsdService fails a client's concurrent second resolve with FAILURE_ALREADY_ACTIVE. - Observable signal: a local _adb._tcp endpoint accepts one A_CNXN packet and returns a structurally valid A_AUTH/ADB_AUTH_TOKEN or A_CNXN packet, or a local _adb-tls-connect._tcp endpoint returns a structurally valid A_STLS packet.
- Producing subsystem: the ADB transport protocol implemented by adbd, reached through the local address and port resolved from NSD.

## Severity semantics

- All clear: no active ADB signal and no contradiction was observed through available sources.
- Warning: ADB is enabled or supporting evidence indicates ADB activity, but there is no persistent hard runtime contradiction.
- Danger: a protocol-confirmed ADB network endpoint, or one of adbd's sockets (`/dev/socket/adbd`, `@jdwp-control`), persists while init.svc.adbd persists as stopped. Each surface is reported as its own finding. service.adb.root never contributes here; System Properties reports it, as danger only together with ro.debuggable=1.
- Info / unavailable: the app lacks enough visibility to evaluate a source.

Danger means the observed AOSP-defined runtime relationship is inconsistent. It intentionally does
not claim which component is wrong or why.
